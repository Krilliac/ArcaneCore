# Area: Atlas real model loading, textures and display tables (foundation, lane A1)

Part of [atlas](atlas.md). Code: `tools/ArcaneCore.Atlas` (`Textures/`, `Core/Materials/`, `Reference/Dbc/Display*.cs`,
`Reference/Client/Models/Packages/`, `Render/Materials/`, `Web/js/materials/`, `Web/js/atx1.js`). Tests: `tests/ArcaneCore.Atlas.Tests`
(`Textures/`, `Core/GeometryWireV2Tests`, `Reference/Dbc/DisplayTablesTests`, `Reference/Client/Models/ModelPackage*`,
`Render/CpuTexturedRasterTests`, `Host/BinaryEndpointTests`, `Host/RepoAssetGuardTests`, `Web/materials.test.mjs`,
`Web/browser.materials.test.mjs`).

Layering: formats (BLP, M2, DBC readers) know nothing of the Atlas host, UI or the live feed; the renderer draws a scene of chunks
and materials and never calls the feed; the tool UI sits above both. Client assets are read from the user's own client and are never
committed or served beyond the loopback host.

## BLP2 decode (`Textures/BlpFile.cs`, `BlpDecoder.cs`, `DxtCodec.cs`)

`BlpDecoder.Decode` reads BLP2 (type 1) with palettized (alpha 0, 1, 4 or 8 bit), DXT1, DXT3, DXT5 and raw BGRA encodings into
straight-alpha RGBA8 (`RgbaImage`, with nearest and bilinear `Sample`). Palettized alpha comes from `alphaDepth` only. A DXT1
"transparent black" index is honoured only when `alphaDepth` is 1. A non-zero `hasMips` means "levels listed": a level is valid only
when its offset and size fit the file and match the encoding; the first invalid level ends the chain and the rest is generated by a box
filter. RGB565 endpoints are widened by bit replication. Limits: 1 to 4096 pixels per side, 64 MiB decoded. Every failure is
`InvalidDataException`.

## ATX1 texture wire (`Textures/TextureWire.cs`, `Web/js/atx1.js`)

`u32 magic "ATX1"`, `u16 version 1`, `u16 format` (1 RGBA8, 2 DXT1, 3 DXT3, 4 DXT5, 5 R8), `u16 width`, `u16 height`, `u16 layers`,
`u8 levels`, `u8 flags` (bit0 has alpha, bit1 alpha is one bit, bit2 generated, bit3 sRGB hint), `u32 jsonBytes` (a 20-byte header),
then per level `u32 byteLength` and the payload padded to 4 bytes, then the JSON metadata (`key`, `path`, `archive`, `source`, `mean`).
`fmt=dxt` returns the file's own DXT blocks when it has them (the browser asks for it only when `WEBGL_compressed_texture_s3tc` exists);
`maxSize` drops the top mip levels host side.

Texture keys: `client:<path>.blp` (a file that exists in the client index), `gen:<scheme>/<args>` (a registered
`IGeneratedTextureSource`; none ship in A1, an unknown scheme answers 404 `unknown-texture-scheme`) and `missing` (an 8x8 magenta and
black checker, so a missing texture is visible and countable).

## ATG1 version 2 and materials (`Core/GeometryChunk.cs`, `Core/Materials/Material.cs`, `Web/js/atg1.js`)

Version 2 keeps the magic and extends the header to 64 bytes (`u32 streamMask`, `u32 batchCount`, two reserved words). Streams follow the
positions in bit order: 0 normal (f32x3), 1 uv0, 2 uv1 (f32x2), 3 color0, 4 color1 (u8x4 RGBA), 5 boneIndices, 6 boneWeights (u8x4),
7 submesh (u16 plus padding). Batches are 16 bytes (`firstTriangle`, `triangleCount`, `material`, `tag`) and cover every triangle or none.
The JSON gains `materials` (`kind`, `blend` 0 to 6, `flags` as an unsigned number, `textures`, `alphaRef`, `color`, `extra`) and, for
model packages, `model`. A chunk without these stays version 1 and byte-identical. The batch tag is the geoset or submesh id in its low 16
bits and the batch priority in its high 16 bits; for an M2 package the priority is the texture unit's signed priority plane (byte +0x01 of
the unit, read back as `(short)(tag >> 16)`), not its shader id (+0x02).

## Browser (`Web/js/materials/`, `renderer.js`, `viewport.js`)

Files: `materials/index.js` (the registry: `registerMaterialKind(impl)`, `materialKind(kind)`), `materials/generic.js` (the real
`generic` kind and the blend and flag tables), `materials/textures.js` (`TextureStore`) and the stubs `terrain.js` (lane A2), `model.js`
(A3), `skinned.js` (A4) and `character.js` (A5), each exporting an empty `register()` that the index calls after it is defined. A lane
fills its stub by calling `registerMaterialKind` from its own `register()`; it edits neither the index nor the renderer. A kind nobody
registered draws as `generic`. An `impl` is `{kind, programs(gl, shaderLib), layout(streams), bind(gl, program, material, ctx, textures),
pass(material)}`: `pass` answers `'opaque'`, `'alphakey'` or `'blend'`, which is how the renderer orders the material pass, and `bind`
sets the state and uniforms of one batch (returning false skips it). The renderer builds the `generic` program through
`impl.programs` and its vertex array from `impl.layout`.

`TextureStore` fetches `/api/bin/texture`, uploads RGBA8 or S3TC levels, keeps a byte budget (`textureBudgetMb`, default 384) with
two-frame pinning (textures used this frame or the last are never evicted to make room for a generated array; at the end of a frame the
budget is a hard limit, so there only this frame's textures are protected and a texture used one frame ago goes after every older one),
evicts least recently used first, dedupes in-flight requests (four at a time) and answers at once with a placeholder
while a texture loads. Nothing is written to browser storage. `renderer.stats` carries `textures`, `textureBytes`, `texturesPending`,
`texturesMissing`, `texturesEvicted`, `textureOverBudget` and `arrayReallocs`. It is the only allocator of GPU textures: a texture with
several layers uploads as a `TEXTURE_2D_ARRAY`, and a lane that generates textures calls `acquireArray(key, {width, height, layers})`,
`growArray(key, layers)` (capacity grows in steps of 64 layers by a GPU-side copy; old plus new bytes must fit the budget or the call
returns false and the caller falls back), `uploadLayer(key, layer, rgba)` and `release(key)`, so generated arrays count against the same
budget (they are never evicted, only released). When the textures a frame uses exceed the budget the store evicts nothing in a loop: it marks
the overflow `textureOverBudget`, asks the host for textures one `maxSize` step smaller (half the configured cap, or half the largest
texture seen) and lets the starved keys retry once at that size; the normal cap returns after 120 frames under 80 % of the budget.

Chunks with batches draw in a material pass (opaque, alpha key, then blended back to front). Back faces are not culled yet: the winding of
real M2 and WMO data is for lane A3 to prove. `textureRadius` (0 to 2, default 1) limits how many tiles around the focus load their `.tex`
layers; when the textures in use exceed the budget the radius also drops by one and returns after 120 frames under 80 % of the budget.

The CPU renderer draws the same chunks through `CpuMaterials` (`generic` registered), with perspective-correct interpolation, alpha key and
blending, deterministically, so `render.png` and `capture` show textured quads headless. `CpuMaterials` is a service (published by the
`RenderMaterialsModule` at foundation order, before the layer modules), so a lane registers a kind from its own module with
`context.Services.Get<CpuMaterials>()!.Register(kind, material)` and `RenderModule` hands the same instance to the renderer. `CpuMaterials`,
`ICpuMaterial` and `BatchShader` are `internal`: that works because every lane's code lives in the Atlas assembly and the test assembly
sees them through `InternalsVisibleTo`; make them public before any lane puts code in another assembly.

## Host (`Core/BinaryEndpoints.cs`, `Core/CacheParticipants.cs`, `Host/AtlasServer.cs`)

`GET /api/bin/{name}?...` runs a registered `IBinaryEndpoint` under the same bearer token as every `/api/*` route and answers
`application/octet-stream` with `X-Atlas-Format` and `Cache-Control: no-store`; errors use the standard JSON error body (400 bad
arguments, 404 unknown key or scheme, 422 rejected file). Endpoints: `texture` (ATX1) and `model` (ATG1 v2, `key=m2:<path>`, `view=0..3`).
Caches register as `ICacheParticipant`; `status` lists each one's count and bytes plus `cacheBytesTotal`, and `cache.clear` empties them.

| Cache | Default budget |
|---|---|
| Parsed client models (existing) | 512 MB |
| Decoded textures | 256 MB |
| Encoded ATX1 | 128 MB |
| Model packages (ATG1 v2 bytes) | 256 MB |
| Layer tiles (existing) | 1 GB |

## Commands

- `texture.get` (`key` or `path`, `fmt?`, `maxSize?`, `mip?`, `out?`): metadata, and a PNG of one mip level written through `OutputPaths` when `out` is given.
- `texture.stats`: cache counts, bytes, hits and misses, and the registered generated-texture schemes.
- `model.info` (`path`, or `kind` + `id`): version, vertices, views, submeshes, texture units, textures (type, flags, path, whether the file exists), bounds.
  Not to be confused with `ref.model.info`, which describes a WMO or M2 for collision (groups, doodad sets, bounding hull).
- `model.package` (`key` or `path`, `view?`, `out?`): summary of the ATG1 v2 package; writes its bytes to `out`. Each batch reports its
  chunk triangle range, geoset (submesh id), signed `priority` and material. The model block's `submeshes[]` give `id`, `firstTriangle`,
  `triangleCount` and `ranges` as positions in the chunk's own triangle array (chunk triangles are emitted per texture unit, so a submesh
  that two units draw appears once per unit in `ranges` and `firstTriangle`/`triangleCount` are its first copy; a submesh no unit draws is
  0/0). A submesh's index start is the 16-bit value at +0x08 plus its level (+0x02) shifted left 16 bits.
- `display.resolve` (`kind` creature, gameobject, item or race; `id`; `gender?` 0 male or 1 female, races only): resolves through the
  display DBCs and answers `modelPath`, `textures` and `problems` plus, per kind:
  - creature: `CreatureDisplayInfo` ([1] model data id, [3] extra id, [4] scale, [6..8] skin names) to `CreatureModelData` ([2] model,
    [4] scale). `scale` is the display scale times the model scale, with a factor of 0 or less counted as 1 (the unscaled rows store 0 or 1;
    this rule is a decision, not a measured client behaviour), reported with `displayScale` and `modelScale`. With an extra row
    (`CreatureDisplayInfoExtra`: [1] race, [2] sex, [3] skin, [4] face, [5] hair style, [6] hair colour, [7] facial hair, [8..17] ten
    equipment display ids, [18] bake name) `extra` carries those values and `bakedTexture` (`Textures\BakedNpcTextures\<bake name>`).
    The equipment slot names are by convention (head, shoulder, shirt, chest, belt, legs, boots, wrist, gloves, tabard); the count is measured.
  - gameobject: `GameObjectDisplayInfo` [1] is the model name.
  - item: `ItemDisplayInfo` ([1] and [2] model names, [3] and [4] their textures, [5] icon, [6..8] geoset groups, [12] and [13] helmet
    geoset visibility, [14..21] the eight armour region textures: arm upper, arm lower, hand, torso upper, torso lower, leg upper, leg
    lower, foot). `item` carries them; models are looked up under `Item\ObjectComponents\{Weapon,Shield,Head,Shoulder,Ammo,Quiver,Pouch,Cape}`
    (the first folder that holds the model). Region texture names are not resolved to files (that is lane A5's job).
  - race: `ChrRaces` ([4] male and [5] female display ids, [15] client file folder) and the gender give
    `Character\<ClientFile>\<Male|Female>\<ClientFile><Male|Female>.m2`.
  Problems are `no-row`, `model-missing`, `texture-missing` and `extra-missing` (the creature names an extra row that does not exist).
  A humanoid's skin variation can name a file that is not there because it wears its baked texture; that is reported as
  `texture-missing` as it is.

Typed DBC readers (`DisplayTables`) cover the eleven tables the lanes need (CreatureDisplayInfo, CreatureModelData,
CreatureDisplayInfoExtra, GameObjectDisplayInfo, ItemDisplayInfo, ChrRaces, CharSections, CharHairGeosets, CharacterFacialHairStyles,
AnimationData, Emotes) and assert each table's measured field count (`ExpectedFieldCounts`) and record size (`ExpectedRecordSizes`), so a
layout change fails loudly instead of reading shifted columns. `WdbcFile` already refuses records that are not four bytes per field; the
record-size assertion pins the measured value per table. The column meanings above were read from the 5875 client's own files and are
pinned by the env-gated real-data tests.

## M2 layout used by the model package

Header offsets of a 1.12.1 (version 256) M2: vertices 0x44, views 0x4C, textures 0x5C, replaceable-texture lookup 0x7C, render flags 0x84,
bone lookup 0x8C, texture lookup 0x94. Records: vertex 48 bytes, inline view 44 bytes, submesh 32 bytes, texture unit 24 bytes, texture
16 bytes, render flag 4 bytes (`u16 flags`, `u16 blend`). The real-data tests check them on the client's own models. Texture unit
fields used: +0x01 priority plane (signed), +0x04 submesh, +0x0A render-flags row, +0x10 texture lookup row; submesh fields: +0x00 id,
+0x02 level, +0x08 index start, +0x0A index count.

Limits of the minimal package: a submesh is drawn once per texture unit, so a multi-layer opaque model emits coplanar duplicate geometry
that z-fights; lane A3 owns the multi-texture shader that replaces it. The alpha-key reference is 0.5; the client's own threshold for M2
blend mode 1 is commonly quoted as about 224/255 and is unverified, to be pinned in A3.

## Tests and real data

Synthetic tests encode their own BLPs, M2s and WDBC tables. Real-data tests are gated on `ARCANECORE_TEST_CLIENT_DIR` (the client
directory, read through its MPQ chain): every listed BLP decodes or is rejected with a reason, with thresholds from a census of the
client; patch-deleted names are not listed; the eleven display tables have their measured shapes; a creature display resolves to an
existing model and textures; a humanoid creature, an item display and both genders of a race resolve to files that exist. Browser tests need `ARCANECORE_TEST_BROWSER` (a Chrome or Edge executable) and fail, not skip, when the
browser lacks S3TC.
