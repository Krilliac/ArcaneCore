# Protocol decisions and reference discrepancies

Where the references (vmangos, cmangos-classic, mangoszero, gtker/wow_messages, wow_srp) disagree with each other, or where ArcaneCore
deliberately differs from them, the choice made is recorded here so the next reader does not re-derive it. The entries were
settled while the logon, world handshake, character, movement, runtime and session features were first built, and each one is
pinned by tests. The rule that produced them is in [contributing](../guide/contributing.md#references-and-citations): when two references
disagree, prefer the one a real 1.12.1 client agrees with, and say so in a comment next to the code.

Reference names below are short for the projects listed in the [roadmap reference set](../ROADMAP.md#reference-set-extended-2026-10-02-and-2026-10-04-at-the-developers-request).
Source locations are as they were read at the time; line numbers are not given because the references move.

## Wire anchors that must not regress

- **Two daemons.** The logon/realm daemon listens on TCP 3724 and the world daemon on TCP 8085 by default. They share the auth database and
  nothing else at run time.
- **Auth is SRP6, WoW variant.** `g = 7`, `k = 3`, the 32-byte WoW prime `N`. The account name and password are uppercased before hashing. The session
  key `K` comes from `S` through the SHA1 interleave. The known-answer vectors (8,005 assertions at the time of writing) come from gtker/wow_srp and run in
  the Cryptography tests.
- **Header encryption is the vanilla rolling cipher, not ARC4.** It is seeded from the SRP6 session key, covers packet headers only, and starts after
  `CMSG_AUTH_SESSION` (`WorldHeaderCrypt`). ARC4 and HMAC-derived keys belong to TBC and later builds.
- **Header sizes.** Server to client: 4 bytes (2-byte big-endian size, 2-byte little-endian opcode). Client to server: 6 bytes (2-byte big-endian size,
  4-byte little-endian opcode). Inbound sizes outside 4 to 0x2800 are rejected (vmangos `WorldSocket::handle_input_header`).
- **Opcodes and update fields are build-5875 specific.** `WorldOpcode.g.cs` and `UpdateFields.g.cs` are generated by `tools/codegen` from vmangos and
  cross-checked against gtker; the script fails on any disagreement. Values from later expansions are wrong and desync the client silently.

## Logon and SRP6

1. **Hashing width is padded, not minimal.** `A`, `B` and `N` are hashed as fixed 32-byte little-endian values, the session key as 40 bytes, the salt as
   32 raw bytes. vmangos hashes the minimal big-number form, which differs only when a value has a leading zero byte (about 1 in 256), a rare login failure that
   retries hide. gtker/wow_srp, which was reverse engineered from the client, and the known-answer rows with leading-zero keys confirm the padded form.
2. **Session-key interleave strips an even number of leading zero pairs.** The client algorithm strips an even count of leading (low-order) zero bytes of the
   little-endian `S` before splitting. vmangos uses a fixed 32 bytes, identical for a full-width `S`. ArcaneCore follows the stripping form
   (gtker `as_equal_slice`, checked against its interleave vectors).
3. **Realm list trailer is `0x0002`.** vmangos writes `uint16(0x0002)` after the realm array; some neutral documents say `0`. ArcaneCore matches vmangos.
4. **Proof success is 26 bytes for builds below 6299:** command, error, `M2[20]`, survey id (u32). A failure is command, error, `uint16(0)`.
5. **Auto-create on login** is the WCell convention (the password must equal the username), is **off** in the shipped realm configuration and is not retail.
   See the [installation guide](../guide/installation.md).

## World handshake

1. **The auth digest hashes the full stored 40-byte session key.** vmangos hashes the minimal form of `K`, which differs only if the most significant byte is zero.
2. **Encryption starts after the digest check.** `SMSG_AUTH_CHALLENGE` and the inbound `CMSG_AUTH_SESSION` carry plaintext headers; `SMSG_AUTH_RESPONSE` onward is encrypted, as in vmangos.
3. **`SMSG_AUTH_RESPONSE` is a single result byte** in vanilla; the billing fields are TBC and later. `AUTH_OK` is `0x0C`.
4. **`SMSG_ADDON_INFO`** is answered from the client's zlib block as vmangos does (Blizzard addons hidden, custom addons visible); a malformed or absent block gives an empty reply and
   the client still proceeds.
5. **There is no `REALM_SPLIT`.** That opcode is TBC and later, and the vanilla client does not send it.

## Objects, update fields and movement

1. **vmangos update-field comments are stale.** The inline hex comments for the PLAYER fields in `UpdateFields_1_12_1.h` are 6 too low. The symbolic
   `UNIT_END + offset` arithmetic is authoritative (`UNIT_END = 188`, `PLAYER_END = 1282`) and is what the generated table reproduces.
2. **Players are created with `CREATE_OBJECT`.** `CREATE_OBJECT2` is for objects spawned into a map (vmangos). The player's power value belongs at `POWER1 + powerType`, not always in the mana field.
3. **Transport block of `MovementInfo`.** vmangos and cmangos write a u64 GUID and a position; mangoszero adds a u32 time and skips the fall time; gtker uses a packed GUID and a u32 time. The vmangos/cmangos layout is used.
4. **`ON_TRANSPORT` is `0x02000000`.** gtker labels `0x200`; every MaNGOS core uses `0x02000000`.
5. **`CHAR_NAME_SUCCESS`** is `0x50` in gtker and `0x52` in vmangos (an extra CONSECUTIVE_SPACES entry). `CHAR_NAME` `0x48` is `ONLY_LETTERS` in gtker and `INVALID_CHARACTER` in vmangos: the same value and meaning.
6. **Visibility** uses 2D distance plus both bounding radii with a strict `<`, a 100 yd range and 1 yd of grey hysteresis once visible (vmangos `IsWithinVisibilityDistanceOf`, `Visibility.Distance.Grey.Unit`).
   A player leaving range gets an out-of-range block (`UPDATETYPE_OUT_OF_RANGE_OBJECTS` = 4); logout uses `SMSG_DESTROY_OBJECT` instead.
7. **Compression.** Update packets above 128 bytes go out as `SMSG_COMPRESSED_UPDATE_OBJECT` (u32 size plus zlib), as vmangos does.

## Session, chat and commands

1. **`SMSG_FORCE_MOVE_ROOT` carries a packed GUID.** gtker lists a full u64 for 1.12; vmangos, cmangos-classic and mangoszero all send the packed form. The three servers win.
2. **Opcode `0x209`** is `SMSG_ACCOUNT_DATA_MD5` (eight digests) in vmangos and `SMSG_ACCOUNT_DATA_TIMES` (u32[32]) in gtker: the same 128 bytes. Without it the chat frame is an unusable white box. The vmangos meaning is used, with real hashes.
3. **`SMSG_UPDATE_ACCOUNT_DATA`** is type, size, zlib (the 1.12 layout vmangos and cmangos-classic agree on). gtker documents only the TBC and later layout.
4. **Security scale.** vmangos uses 0 to 7; cmangos-classic and TrinityCore use 0 to 3. ArcaneCore uses 0 to 3 and carries config defaults over by meaning (instant logout for moderators, GM in the who list for administrators).
5. **Say and emote range** is 25 yd in vmangos and cmangos code defaults and cmangos' shipped config; vmangos' shipped config raises both to 40. 25 is used.
6. **Logout.** The 20 second countdown is an option in ArcaneCore (vmangos hard-codes it). `CMSG_LOGOUT_CANCEL` only undoes a logout in progress (vmangos also stands up a merely sitting player).
7. **Staff cannot act on higher accounts** (`.kick`, `.modify money`). cmangos and vmangos allow it unless `GM.LowerSecurity` is set; ArcaneCore always checks.
8. **Account data** is accepted in every authenticated state (vmangos: logged in or recently logged out) because it belongs to the account either way.
9. **A faulty command** replies with an error and is logged; it never drops the GM's connection.
10. **Money cap** is `0x7FFFFFFF - 1` (`MAX_MONEY_AMOUNT`).

## Runtime and persistence

1. **One authoritative world tick of 50 ms** (vmangos `WORLD_SLEEP_CONST`), with autosave every 15 minutes (`PlayerSave.Interval`). In-world packets wait for the next tick, as in vmangos.
2. **One session per account.** A reconnect kicks the stale one, and login waits for a lingering copy of the character to leave the world (vmangos `World::AddSession_`).
3. **Slow clients** are disconnected when their outbound queue passes 8 MiB; a slow socket never stalls a map.
4. **Schema evolution fails closed.** Each component keeps a version row; anything the startup bootstrapper cannot apply as a known step stops the daemon ([database upgrade](../ops/database-upgrade.md)).
   Shared-database creation with `EnsureCreated` skipped a context as soon as the database had any table, which is why schema creation is per component.
5. **Toolchain.** The EF Core and Extensions packages stay at version 9 because the Pomelo MySQL/MariaDB provider (the primary engine) had no .NET 11 release; EF 9 runs on net11.0
   (`Directory.Packages.props`).
