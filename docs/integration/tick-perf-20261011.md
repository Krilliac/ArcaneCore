# World tick: capacity for ~1000 bots (2026-10-11)

Branch `claude/w22-tick-perf`. Input: the TickMonitor lines (PR #112) and the `Perf:9001` slow-update lines of the live
deploys `live-w20-r1` .. `live-w22-r4` (203-232 managed bots). **Every before/after number below comes from a test harness in
this repository on the shared development machine, not from the live server**; the harness is named with each number.

|---|---:|---:|---:|---:|

## Changes

1. **Scourge Invasion / War Effort store work off the world thread** (`OffThreadStoreWork`, `ReadSnapshot`). The five-second
   refresh blocked the world thread on a Serializable SQLite transaction (Microsoft.Data.Sqlite: `BEGIN IMMEDIATE`, the write
   lock) behind the character save queue, with or without an invasion running. Now a single-flight pool job, applied through
   `WorldRuntime.Post`; the polls read in a deferred transaction; `StopAsync` writes what is still queued. vmangos keeps event
   state in memory (`ObjectMgr::m_SavedVariables`) and saves through the async `PExecute` queue.
   Harness `ScourgeInvasionTickBoundTests.MeasureTickCostWithASlowStore` (200 ms per store call): slowest tick 219 ms inline
   (the old behaviour) vs 0.2 ms; `WorldStateReadSnapshotTests`: the load returns under a held write lock (the old load:
   `database is locked` after ~30 s).
2. **Visibility pass only past the relocation lower limit** (`World:Maps:VisibilityRelocationLowerLimit`, 10 yards; vmangos
   `Unit::OnRelocated`, a Unit rule: game objects keep a pass per move). Harness
   `VisibilityRelocationLowerLimitTests.MeasureCrowdedVisibilityPhase` (200 players + 1 500 creatures, 0.35 yd a tick):
   visibility phase 12.06 -> 0.42 ms/tick.
3. **Navmesh A\* on reused per-thread state** (`NavMeshQuery.FindCorridor`, `NavMesh.CollectNeighbours`). The 200-bot benchmark's
   allocation sample put 4.9 GB of neighbour iterators, 3.2 GB of node arrays and 2 GB of node-index entries per 60 s in the bot
   path search. Harness `NavMeshSearchCostTests` (300 seeded queries on the real Elwynn/Westfall navmesh): identical corridors
   (fingerprint `F06FE607385E10D1` before and after, plus a fresh-search oracle), 3 824 -> 12.7 KiB allocated per query.
4. **Saved-variable writers off the world thread** (`StateSaveQueue`): Dragons of Nightmare, Fishing Extravaganza, elemental
   invasion, Silithyst; each `StopAsync` writes what is queued (`WorldStateSaveFlushTests`, `StateSaveQueueTests`).
5. **Continents update only the creatures in the active cells** (`World:Maps:UpdateActiveCellsOnly`; vmangos
   `Map::UpdateActiveCellsSynch`), with vmangos' active objects (script command 21, LARGE/GIGANTIC/INFINITE_AOI, cmangos
   ACTIVE, formation members). Harness `ActiveCellUpdateTests.MeasureCreatureUpdatesWithFewPlayers` (938 wanderers, 2 players):
   3.11 -> 0.32 ms/tick. Instances and battlegrounds keep updating every creature (vmangos activates 170/180 yards there;
   ArcaneCore has one 100-yard activation distance) - a deliberate deviation. A non-player active object loads and pins only its
   own grid (vmangos Map::AddToActive; cells around it are updated where already loaded, SetNoCreate); only players load the
   grids around them. 200-bot benchmark: loaded grids map 0/1/369 20/14/6 -> 16/12/5, CreatureMapSystem 1.93 -> 1.62 ms/tick.

## 200-bot terrain benchmark

`ManagedPlayerbotTerrainBenchmarkTests` (`ARCANECORE_BOT_BENCH=200`, 60 s warm-up, 60 s hold, a copy of the live world.db,
workstation GC). Its whole-tick numbers are dominated by bot-think spikes and vary a lot between runs; read the per-phase
columns. Before the navmesh change (two runs): tick mean 25.8 / 41.8 ms, p99 152 / 502 ms, bot-feature allocation 15.3 /
23.5 MB per tick, GC pause 1 395 / 1 612 ms per 60 s. After: 17.6 ms, 75 ms, 0.87 MB, 472 ms. Visibility phase 1.35 -> 0.31
ms/tick (limit 0 vs 10); CreatureMapSystem 3.00 -> 2.02 ms/tick (active cells off vs on, before the active-object flags).
