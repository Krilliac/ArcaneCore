# Bot-think allocation cuts (perf-tick lane, 2026-10-19)

Measured first, then changed. Live build 120ea4381, the 200-bot real-terrain benchmark and BenchmarkDotNet on one machine
(Ryzen 9 9900X3D), with other lanes building beside it, so wall times are noisy and allocation counts are the firm numbers.

## What the measurements showed

- **Live world (<live-home> logs).** The bot think budget (12.5 ms per tick) ends every tick, about 35 thinks run per tick,
  and the process allocates about 2.8 MB per tick (Server GC pauses about 15 ms). The "Slow map update" lines put
  CreatureMapSystem first (mean 39.9 ms when present), then visibility, GameObjectMapSystem and StealthDetectionUpdater. Those
  per-updater times include the wait for the serial map gate, so they are not clean attribution.
- **Creature walk (`CreatureTickBenchmarks`, new).** 8,000 synthetic creatures on map 0: 715 us per tick with 64 players, 5.84 ms
  with 512 players, 11 KB allocated per tick. CreatureMapSystem is about 95% of the tick, and an instrumented run spread its
  per-creature cost over AI, spline advance, random motion and motion selection with no single hot spot. Not changed.
- **Bot think allocations.** A `dotnet-trace` gc-verbose capture of the 200-bot benchmark (45 s, 1,282 MiB sampled) put the
  quest-candidate scan on top: `Func<ushort, bool>` from the game-event spawn gate (114 MB, via `PlayerbotWorldDestinations.IsPresent`),
  the closure in `QuestNpcServices.MissingAdapters` (41 MB), and the closures and visited set of `CanTakeQuest` (about 50 MB together).

## Changes (behaviour unchanged)

| Path | Was | Now |
|---|---|---|
| `GameEventSpawns.Allows` | `events.Any(_state.IsActiveEvent)`: a delegate per ask | `AnyActive` loop |
| `QuestNpcServices.MissingAdapters` | lambda over the adapter modules: a closure on every call | `ModuleCoversEventQuest` loop, still read per query |
| `QuestNeeds.Of` | LINQ `Any` over `ReqSourceId` / `ReqSourceCount`: enumerators | `AnyNonZero` loop |
| `RefuseTakeQuest` | closures for the exclusive group, previous quests, previous chain and dependent breadcrumbs; a new `HashSet` per top-level call | loop helpers; the visited set is made only when a breadcrumb recurses (seeded with the outer quest, as before) |
| `PreviousQuestSatisfied` | local function converted to a delegate for `All` | static local function in a loop |

## Results

BenchmarkDotNet, `--filter "*QuestCandidate*"` (default in-process job), through the slot runner:

| Benchmark | Before | After |
|---|---|---|
| SpawnGate (two listed givers) | 24.35 ns, 112 B | 14.34 ns, 0 B |
| IsRewardable | 45.68 ns, 32 B | 47.44 ns, 0 B |
| CanTakeQuest (every relation check) | 68.82 ns, 464 B | 39.16 ns, 0 B |

`ManagedPlayerbotTerrainBenchmarkTests`, 200 bots, warmup 40 s, hold 60 s, the same world database copy:

| Run | alloc KiB/tick | botfeature alloc KiB/tick | mean / p99 ms |
|---|---|---|---|
| before (run 1) | 1297.6 | 1260.1 | 7.018 / 20.4 |
| before (run 2) | 1310.5 | 1272.9 | 7.982 / 24.4 |
| after | 986.2 | 946.9 | 6.935 / 19.8 |

The bot feature allocates about 25% less per tick. Tick times are within run-to-run noise.

## Tests

`QuestTakeCheckTests` pins the relation checks that were rewritten (negative exclusive groups, signed previous quests, positive
exclusive groups, chains, breadcrumb chains and dependent breadcrumbs). It also asserts with `AllocationProbe` that `CanTakeQuest`
and `IsRewardable` allocate nothing. `GameEventSpawnTests.AllowsCreature_OnListedGuids_AllocatesNothing` does the same for the
spawn gate. The four allocation tests failed on the old code (CanTakeQuest 59,392 to 69,120 bytes per window, IsRewardable 12,288,
spawn gate 14,336) and pass now.

## Limits

- A breadcrumb's own check still allocates the set of quests on its path. Breadcrumbs are rare, and the set keeps the cycle guard.
- Not changed: `PlayerbotBrain.CollectTargets` (a `Func<PlayerbotHazard, bool>`, 26.6 MB in the trace), the LINQ in
  `FindDefensiveAttacker`, the arrays and enumerators in `HasQuestCandidate`, and the creature walk.
- The live per-updater times stay contaminated by the map gate wait until the gate acquire is timed separately.
