# World tick load benchmark and bounded optimizations (2026-10-08)

Base: `92966fdd`, lane `cx2-perf-tick` (Codex wave 2, committed by the intake review on `codex/w2-perf-tick`). No server, database, schema,
protected playerbot/class/talent/proc code, or reference data was modified.

## Outcome and limits

Two measured costs are reduced: rebuilding player visibility candidate lists (about 344 KB/tick in this fixture),
and reconstructing the heartbeat unit snapshot by scanning the entire map every tick. The full visibility oracle
and heartbeat lifecycle tests still pass. This is **not proof that the live 177 ms p99 / 243 ms maximum is fixed**:
the warm fixture did not reproduce those numbers, and its post-change tail remains variable even without GC.
Cold terrain/collision loading remains synchronous and was the largest measured stall; it is not moved off-thread
by this change. Doing that safely needs a separate tile ownership/readiness design.

## Reproduction

Before building, check free RAM and wait below 3 GiB:

```powershell
(Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory/1MB
dotnet build ArcaneCore.slnx -c Release -m:1 -nodeReuse:false
$env:ARCANECORE_TEST_TERRAIN_DIR = 'D:/ArcaneCore-data/terrain-5875'
$env:ARCANECORE_TICK_CSV = "$PWD/artifacts/perf-tick/run.csv"
# Create the output directory first. The test writes only to the explicitly requested CSV path.
dotnet test tests/ArcaneCore.Game.Tests -c Release --no-build --filter FullyQualifiedName~WorldTickLoadTests --logger 'console;verbosity=detailed'
python tools/perf/summarize_tick.py artifacts/perf-tick/run.csv
```

The CSV switch is optional. Without the terrain variable the same synthetic world runs with collision queries
explicitly disabled. A configured but unusable terrain root fails the test; real ground height, blocked abbey sight,
loaded vmap/mmap tiles and actual mesh paths are asserted so fallback cannot masquerade as coverage.

The benchmark uses seed 5875, 66,000 synthetic `TestUnit` objects on map 0 with 70% clustered around 60 hubs,
670 moving units, six simulated players moving near Northshire, and two existing synthetic ship routes
(one crosses to map 1). Five path queries burst every 20 ticks. Each tick also performs six terrain height,
six model height, and six line-of-sight queries when terrain is enabled. All simulation uses manual 50 ms steps:
100 warmup ticks followed by 600 measured ticks (35 seconds of simulated world time). No sleeps, quiet-window
assumptions, or wall-time correctness thresholds. Timing uses `Stopwatch`, allocations use the current thread's
allocation counter, and GC counts are process-wide generation collection deltas. Nearest-rank percentiles.

The internal `WorldRuntime.RunTick` overload observes the same map update pipeline as the public method.
CSV columns cover complete tick time, bytes, GC 0/1/2, commands, world features, map simulation, visibility,
values, flush, cleanup, cold loading, terrain, vmap and pathfinding. Map timings aggregate maps; terrain/vmap/path
are **subsets** of simulation, not additional tick phases. Transport updates run as the existing world feature.
Rows for cold/warmup ticks are retained; summaries do not silently drop them from the artifact.

These are synthetic population/visibility tests, **not** full creature AI, managed bot decision-making,
network session processing, spell/combat scripts, database traffic, autosave, passenger boarding, or long-distance
multi-tile pathfinding. Units remain in map memory even in unloaded grids, as in `VisibilityPerformanceTests`;
this deliberately stresses the map-wide scan more than a production creature grid loader would. The query fixture
loads one Northshire tile directly and does not measure the production grid lifecycle's collision attachment.
Ships use `TransportTestKit`, not invented ClassicDB content or a claim of real route coverage.

## Measurements

Windows, SDK 10.0.401, runtime 10.0.12, Release, identical harness and optional terrain directory before/after.
Each row is a separate process with 600 measured ticks. Other lanes share the workstation; no CPU isolation was
imposed. Raw evidence is retained locally under `artifacts/perf-tick/` (ignored by git), including every CSV,
build/test log and `summary.jsonl`; `tools/perf/summarize_tick.py` reproduces the numbers. Times below are ms.

| Run | Mean | p95 | p99 | Max | Bytes/tick | GC 0/1/2 |
|---|---:|---:|---:|---:|---:|---|
| before | 3.451 | 6.692 | 8.320 | 16.265 | 363671 | 5/1/0 |
| before-2 | 3.193 | 5.682 | 9.429 | 30.777 | 363672 | 4/0/0 |
| before-3 | 3.167 | 5.515 | 8.715 | 11.931 | 363682 | 4/0/0 |
| final-1 | 2.261 | 3.336 | 5.900 | 18.436 | 19873 | 0/0/0 |
| final-2 | 2.295 | 4.288 | 6.400 | 9.167 | 19867 | 0/0/0 |
| final-3 | 2.646 | 4.137 | 14.990 | 48.742 | 19866 | 0/0/0 |

`before` and `before-3` ran with no build/test launched concurrently by this lane. `before-2` overlapped the
regression-test compilation, causing three MSB3026 DLL-copy retries; retained for transparency but excluded from
performance conclusions. Final runs were sequential after the final build and before the full suites.
The `tick-after*.csv` artifacts are the intermediate visibility-only change, not the final implementation.

Across the two uncontaminated baseline runs, mean was 3.167-3.451 ms; final means were 2.261-2.646 ms.
Allocation fell from 363,671-363,682 to 19,866-19,873 bytes/tick (about 94.5%). Final runs had no measured GC.
The first two final p99s improved, but the third rose to 14.990 ms and maximum 48.742 ms: no universal tail-latency
improvement is claimed. That run's slowest tick spent 38.570 ms in visibility with no GC collection; elapsed timings
cannot distinguish CPU execution from OS descheduling/JIT. A live CPU trace is still needed for attribution.

Measured simulation mean (including heartbeat/movement/queries) was 1.617-2.161 ms before and 0.717-0.949 ms after.
Visibility mean did not consistently improve (baseline 1.282-1.542 ms; final 1.295-1.871 ms); its deterministic win
is allocation removal. Short path queries were not the dominant warm cost: baseline path-phase p99 was
0.594-1.418 ms per tick, versus the large non-path simulation cost. No path algorithm change was justified here.

Cold first-tick total/load times: baseline 1765.790/1578.614 and 371.397/258.177 ms; final
464.827/328.161, 409.562/246.891, 404.445/251.146 ms. These are cold **provider instances**, not controlled cold OS
file caches. Parsing, file I/O, initial JIT and scheduling are combined. They demonstrate a synchronous load stall,
not a measured disk-only cost or an improvement from these optimizations.

## Changes and fidelity references

- `src/ArcaneCore.Game/Maps/Map.cs`: reuse a player visibility candidate list after warmup. The list is cleared in
  `finally`; nested visibility refreshes get an independent list. Nearby objects, the old visible set, observers,
  remote camera candidates, de-duplication, join ordering, distance/grey-distance and visibility rules are preserved.
  References: `D:/refs/vmangos/src/game/Maps/Map.cpp`, `Map::UpdateObjectVisibility` (1636);
  `D:/refs/vmangos/src/game/Objects/Player.cpp`, `Player::UpdateVisibilityOf` (18775, 18899).
- `Map.cs`: cache the heartbeat unit snapshot until a unit/player joins or leaves. Rebuild from dictionary order
  before heartbeat delivery; callbacks can mutate membership without changing the in-flight snapshot. Removed units
  are still skipped, new units begin next tick, quest-settlement players are still excluded, and timers are untouched.
  Internal `HeartbeatSnapshotObjectsVisited` counts dictionary work for deterministic complexity regression checks.
  References: `D:/refs/vmangos/src/game/Objects/Object.cpp`, `WorldObject::Update` (1534);
  `D:/refs/vmangos/src/game/Objects/Unit.cpp`, `Unit::Heartbeat` (347). Snapshot caching is an ArcaneCore implementation
  optimization, not a new retail behavior port.
- `src/ArcaneCore.Game/Maps/WorldRuntime.cs`: internal optional map-diagnostics observer for the test harness.
  Public `RunTick` retains its behavior; diagnostics are created when observed or when existing warning logging needs them.
- `tests/ArcaneCore.Game.Tests/GridTerrain/WorldTickLoadTests.cs`: serial benchmark collection and CSV measurements.
  Real query coordinates reuse `RealTerrainDataTests`' ClassicDB human start/abbey positions; ship behavior uses the
  existing `TransportTestKit` / `TransportSystem` (`vmangos src/game/Transports/Transport.cpp`, `ShipTransport::Update`).
- `tests/ArcaneCore.Game.Tests/GridTerrain/VisibilityAllocationTests.cs`: stable population allocation budget and
  recursive/throwing-rule lifecycle checks.
- `tests/ArcaneCore.Game.Tests/GridTerrain/HeartbeatSnapshotTests.cs`: stable-map work bound, heartbeat callback
  mutation, and player leave/rejoin timer preservation.
- `tools/perf/summarize_tick.py`: stdlib CSV summarizer, all phases and worst rows retained for inspection.
- `docs/areas/ops-perf.md` and this report: reproduction, evidence and scope limits.

## Database investigation and remaining work

A bounded scan of Game/World (excluding Playerbots) for synchronous task waits, file reads and `SaveChanges` found
startup/attachment content reads plus terrain/vmap/mmap file reads. Spot checks of `EconomyFeature.Attach`,
`ReputationFeature.Load`/`ReportStatus`, and `WorldHost.StartAsync` confirm attachment runs before the world thread.
`CharacterSaveQueue` uses a background channel consumer. This is not a proof that all feature handlers avoid
blocking: the benchmark has no database, and this scan does not catch every synchronous provider/API or lock.
No database bottleneck was established, so no persistence semantics were changed. Scan evidence is
`artifacts/perf-tick/tick-blocking-scan.jsonl`.

No content rows or schema versions are needed by the optimization. Optional real probes need `maps/`, `vmaps/`,
and `mmaps/` beneath the terrain variable; nothing is copied or written there. No new ClassicDB rows are invented.
To account for the reported live tail, the coordinator still needs a representative full-feature/managed-bot run
with the actual content and a CPU/GC/I/O trace, correlated with existing `.server info` phase diagnostics. In
particular: creature AI/casts, managed-bot decisions, long routes, tile crossings, autosave and database stalls are
not qualified by this fixture. The fixture's warm 177 ms p99 was **not reproduced**.
