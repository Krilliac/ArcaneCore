# Multi-version and multi-expansion support (design)

Status: draft for review. Docs only, no code change.
Base: `integrate/wave17` @ `ecd5b3e`.

Goal: one ArcaneCore server that accepts every client from 1.12.1 (5875) through 2.4.3 (8606) and 3.3.5a (12340), and possibly other builds later (1.12.2 5878/6005, 3.0.x and so on). Content lives in one unified world database, and rows can be specific to a build range or an expansion.

Takeaways:
- The *build check* is tiny: about 6 call sites. The *build assumption* is everywhere: the opcode enum values, the update-field indexes and the packet layouts are compile-time constants used directly by about 240 files.
- Inline `PacketWriter` building in handlers is the main refactor cost. There are about 323 writers in about 107 files.
- Game logic does not branch on version anywhere today. That's good: there's nothing to untangle, only to abstract.

## 2. Prior art

AscEmu (`compare/asc/src`):
- `world/Version/Opcodes/OpcodeTable_{Classic,TBC,WotLK,Cata,Mop,WoD,Legion}.cpp` plus `OpcodeTable.cpp` and `OpcodeMeta.cpp`: a *logical* opcode enum (`Opcodes.hpp`) mapped at runtime to a per-version wire value. A session picks its table from the build.
- `world/Server/Packets/` has 756 packet classes, each with `serialise`/`deserialise` and `#if VERSION_STRING` branches inside. There are 1906 `#if VERSION_STRING` sites repo-wide, and the build is still chosen at **compile time** (`logonserver/LogonConf.hpp.in`). Lesson: the logical-opcode table is a good idea. The compile-time selection and the scattered `#if` blocks are what we must avoid.
- Update fields are per-version generated headers, selected the same way.

TrinityCore 3.3.5 and AzerothCore: a single build (12340), with a `UpdateFields.h` and opcode table per branch. Their `WorldPackets::*` classes (`Server/Packets/*.h`, `Read()`/`Write()`) are a clean model for typed packet structs.

cMaNGOS: separate repositories (`mangos-classic`, `mangos-tbc`, `mangos-wotlk`) that share most game code by hand-porting commits between them, plus separate DBs (classic-db, tbc-db, wotlk-db). Lesson: the per-version *divergence* is mostly protocol, DBC layout, spell/aura enums and content. Core logic is about 80% shared. The cost is keeping three forks in sync, which is exactly what one runtime-selected core avoids.

## 3. Proposed architecture

```
 client ──► Realm (auth adapter by build) ──► World session
                                          │ build from CMSG_AUTH_SESSION
                                          ▼
                        IClientProtocol (per build)
             opcodes · header crypt · update fields · packet serializers · movement codec
                                          ▼
                 version-neutral core model (Game/World)
                                          ▼
     IClientData (per-version DBC/DB2 set) + ContentGate (expansion level)
                                          ▼
                 unified world DB (rows carry min_build/max_build/expansion)
```

### 3.1 Version-neutral core model
- `Game` works in logical terms: `LogicalOpcode`, `ObjectField`/`UnitField`/`PlayerField` *semantic* ids (for example `UnitField.Health`), `AuraKind` (a logical aura enum, a superset of all supported versions), and neutral `MovementState`.
- Handlers emit typed messages (`SmsgMonsterMove`, `SmsgSpellGo`, ...) instead of raw `PacketWriter`. Each record holds the superset of fields, and the serializer drops what its build lacks.
- `ClientBuild` turns into a value type (`ClientBuildInfo { Build, Expansion, Version }`) carried on the session. The `const` stays for 5875 back-compat.

### 3.2 Protocol adapter for each client build
`IClientProtocol` (in `ArcaneCore.Protocol`), registered by build in an `ClientProtocolRegistry`:
- `IAuthProtocol`: the logon challenge/proof layout. 2.4.3 and 3.3.5 add the 2FA/PIN flags and a different realm list (the realm list adds `lock`, `flags`, version fields for 8606/12340). SRP6 math is shared (`Srp6Math`). Proof hashes and version-check (`ClientIntegrity`) tables differ for each build.
- `IOpcodeMap`: logical ↔ wire, generated by `gen_wow_tables.py` from one source list per build (`WorldOpcode.5875.g.cs`, `.8606.g.cs`, `.12340.g.cs`).
- `IWorldHeaderCrypt`: 1.12 and 2.4.3 use the xor/add scheme (TBC with HMAC-seeded key); 3.3.5 uses RC4 (ARC4-drop1024) with the server/client HMAC keys. 3.3.5 also has the large-packet header bit.
- `IUpdateFieldLayout`: semantic field → index/size/flags per build. `UpdateMask` and the values-update builder take the layout. Create-block and movement-block flags (`UPDATEFLAG_*`) differ; 3.3.5 adds packed GUIDs everywhere and the `SMSG_COMPRESSED_UPDATE_OBJECT` thresholds.
- `IPacketSerializer<T>` for each typed message and build. The default implementation is shared, and builds override only what differs.
- `IMovementCodec`: MovementInfo layouts (TBC adds flags2-less extra fields; WotLK adds `MovementFlags2`, transport seat/time2, and spline flag renumbering).
- Picked per session: the Realm reads `Build` from the logon challenge and the World reads it from `CMSG_AUTH_SESSION`. An unknown build is rejected with today's error codes. The session binds `IClientProtocol` once and never switches.

### 3.3 Client data layer for each version
- `IClientDataSet` per expansion: `ClientData:Paths:{5875|8606|12340}` with DBC layouts generated per build (`gen_dbc_layouts.py --build N`). Catalog row types (SkillRows, TalentCatalog, ...) become neutral records with a per-build reader.
- Maps, vmaps and mmaps: the 1.12 maps cover a subset. Outland (530) and Northrend (571) need TBC/WotLK extracts. The extractor runs on the newest client data and writes one terrain set; older clients only ever see the maps their expansion allows.
- Server-side spell data: keep one `spell_template` row per spell id per build range (see §4), because the same id can differ between 1.12 and 3.3.5.

### 3.4 Expansion gate for content
- `realm.max_expansion` (0 classic, 1 TBC, 2 WotLK) and `account.expansion` (already standard in TC/cMaNGOS). Effective level = min(realm, account, client build expansion).
- `ContentGate.IsVisible(row, session)`: checks `expansion` and `[min_build, max_build]` and is applied by loaders and per-session queries (vendor lists, quest givers, trainers, item queries, map entry, level cap 60/70/80).
- Shared world, mixed clients: creatures and objects outside a client's range simply aren't sent to that client (a visibility filter), and their maps can't be entered.

## 4. Unified DB schema
- Content tables (`creature_template`, `creature`, `gameobject_template`, `gameobject`, `item_template`, `quest_template`, `npc_vendor`, `npc_trainer`, loot tables, `spell_template` overrides, `game_event`, conditions) gain:
  - `min_build SMALLINT UNSIGNED NOT NULL DEFAULT 0` and `max_build SMALLINT UNSIGNED NOT NULL DEFAULT 65535` (inclusive), and
  - `expansion TINYINT NOT NULL DEFAULT 0` (the minimum expansion for which the row exists).
  - The primary key extends to `(entry, min_build)` on tables where the same id genuinely differs between versions (item_template, quest_template, creature_template, spell overrides). Spawn tables keep their guid PK and use the build columns as a filter only.
- Resolution rule: for a given build, take the row with the greatest `min_build ≤ build ≤ max_build`. Ranges for the same key must not overlap, which the `DbUpgrade` validation enforces.
- Import merge (ClassicDB → TBC-DB → WotLK-DB style):
  1. Import ClassicDB as today with `min_build=0, max_build=65535, expansion=0`.
  2. Import TBC-DB. For each key: identical to the classic row → no-op; absent from classic → new row, `expansion=1, min_build=8606`; different → close the classic row (`max_build=8605`) and insert the TBC row (`min_build=8606`). Rows the TBC DB removed: set `max_build=8605`.
  3. Same for WotLK at 12340 (or at the lowest supported 3.x build).
- Conflict rules: (a) the newer DB wins inside its range, older ranges stay untouched; (b) spawn guids are namespaced per source (classic keeps its guids; TBC/WotLK imports are offset or remapped through a `guid_map` table, so re-imports are idempotent); (c) script names and AI bindings follow the row; (d) hand-written ArcaneCore overrides (the `*_override` tables and the wave fixes) always beat imported rows and carry their own build range; (e) the importer writes a conflict report instead of guessing when columns that don't exist in the older schema can't be mapped.
- Characters DB: version-neutral. It adds `characters.created_build`, and fields specific to an expansion (arena teams, achievements, glyphs, DK runes) live in new tables that only matter for TBC/WotLK sessions. A 1.12 client can't log in a character above level 60 or one on map 530/571 (it's shown as locked in the char enum).
- Migrations from the current schema: world 47 adds the build/expansion columns with defaults, so every existing row is unchanged and visible to 5875. world 48 extends the PKs. auth 6 adds `account.expansion` and `realmlist.max_expansion`/`allowed_builds`. characters 49 adds `created_build`. These are all additive and default to today's behaviour.

## 5. Staged migration plan

Each stage is a set of small PRs. 1.12 must stay fully green after every PR (Game/World suites plus the imported-content gate). Estimates are worker-days for one focused worker.

| Stage | Content | Effort | Exit check |
|---|---|---|---|
| S0 | Extract `IClientProtocol` around today's 5875 code: opcode map (logical = 5875 values at first), header crypt, auth protocol, update field layout, movement codec. Bound per session from the build. **Zero behaviour change**, and byte-for-byte packet tests via MockClient/Sniff replays | 4–6 | All suites green; replay diff empty |
| S1 | `ClientBuildInfo` on sessions, realm/account expansion columns (auth 6), `ContentGate` that always passes, and the build-column migrations (world 47/48, characters 49) with defaults | 3–4 | Green; schema upgrade tested from 46 |
| S2 | Typed messages for the hot packets (update object, movement, spells, chat, char enum, login): move the ~323 inline writers behind serializers in batches of about 20 files | 10–15 | Green after every batch |
| S3 | 2.4.3 auth and realm list (SRP proof, integrity table, realm list layout); the client reaches the char screen | 3–5 | Real 8606 client logs in and lists realms |
| S4 | 2.4.3 world login: header crypt, opcode table 8606, char enum/create, update fields 8606, movement codec; enter world on Kalimdor/EK | 8–12 | Walk, chat, log out on 2.4.3 while 1.12 stays green |
| S5 | TBC client data (DBC layouts 8606, Outland maps/vmaps/mmaps), spell/aura enum mapping, TBC-DB import merge, level 70, gate on | 15–25 | Outland questing smoke test |
| S6 | 3.3.5a: auth, RC4 crypt, opcode table 12340, update fields, movement flags2, packed GUIDs, compressed updates | 10–15 | 3.3.5 enters world |
| S7 | WotLK data and content: DBC 12340, Northrend terrain, WotLK-DB merge, DK start, vehicles (S7b), achievements (S7c) | 30+ | Northrend smoke test |
| S8 | Expansion systems: arenas, flying mounts, gems/sockets, glyphs, dual spec, LFG 3.3 | open-ended | per system |

Total to "3.3.5 logs in and plays shared content" (S0–S6): about 55–80 worker-days. Full WotLK parity is a multi-month project.

Risks:
- **Scope.** WotLK systems (vehicles, phasing, achievements) dwarf the protocol work. Mitigation: gate them per expansion and ship protocol support first.
- **Regression on 1.12** from the S2 refactor. Mitigation: byte-exact replay tests in S0, before anything moves.
- **Mixed-version shared world.** Visibility and grouping between a 1.12 and a 3.3.5 player (unknown spells, items, display ids). Mitigation: start with realms limited to one build each, and make mixed realms opt-in.
- **Spell id collisions.** The same id means different spells across versions. Mitigation: build-ranged spell data and a per-build `SpellInfo` cache.
- **Content-DB licences and quality.** TBC-DB and WotLK-DB style imports differ in schema. Mitigation: the importer works per source with conflict reports.
- **Performance.** An extra indirection per packet and field. Mitigation: per-session cached arrays, no virtual calls in the update-field hot loop (layout arrays indexed by semantic id).
- **Client data availability.** Each build needs extracted data. Optional data stays optional per version.

## 6. Decisions

Decided by the maintainer on 2026-10-10:
1. **One build per realm.** Mixed-build realms aren't planned (a realm carries `allowed_builds` with exactly one build).
2. **Builds:** 5875, 8606 and 12340 only.
3. **Aura model:** one combined logical aura enum, a superset of all three versions, with a per-build wire mapping.
4. **Content source per expansion:** TBC from cMaNGOS tbc-db. WotLK from cMaNGOS wotlk-db, with AzerothCore as the gap-fill source. See [6.1](#61-content-source-per-expansion-decision-4).
5. **Primary keys:** template tables extend their key with `min_build`.
6. **Characters across versions:** an operator option, off by default. See [6.2](#62-characters-across-versions-decision-6).
7. **Priority:** S0 through S2 now. S3 and later are on hold.
8. **Default `realm.max_expansion`:** 0 (classic).

Decisions 4 and 6 were written on 2026-10-10, from the survey below and the maintainer's go-ahead.

### 6.1 Content source per expansion (decision 4)

| TrinityTBC, TBC-DB, OregonCore | 2.4.3 | archived or inactive since 2016–2021 | – | – | rejected |

Decision:
- **TBC: cMaNGOS tbc-db, as the only source.** It is the only maintained 2.4.3 database. Its schema is the classic-db lineage the importer already reads (EventAI, `dbscripts_on_*`, `creature_movement`, `spawn_group`, the cMaNGOS `conditions` table), so S5 needs one more `ContentDialect`, not a new importer. AzerothCore's Outland content is in its 3.3.5 state, so it is not a TBC source.
- **WotLK: cMaNGOS wotlk-db as the primary import.** It keeps classic → TBC → WotLK in one lineage, so the per-build `min_build` merge can treat "identical to the earlier row" as a no-op. Rows from a different lineage never compare equal, and most of the classic world would come out as "changed".
- **AzerothCore as the WotLK gap-fill source, not a second full import.** Its world is clearly fuller: about 2.3 times the spawns of classic-db across four maps, and 52,768 SmartAI rows. S7 diffs coverage per zone and per map against wotlk-db and imports what wotlk-db lacks: spawns, waypoints and SmartAI scripts. The SmartAI engine (slices 1–2, smart_scripts world 48/51) runs the imported scripts, and the gap-fill rows carry their source in the import report. Port no AzerothCore AGPL-3.0 file (`src/server/game/TC9Sidecar`, `Trainer.cpp/.h`, `NPCPackets`, two scripts): they would add AGPL's network-source obligation.
- **TrinityCore 3.3.5 is not used.** It has the same schema family as AzerothCore with less activity.
- **Revisit when S7 starts.** If wotlk-db's gaps turn out to be most of Northrend, make AzerothCore the WotLK primary instead. That costs a TrinityCore-schema dialect (conditions, `waypoint_data` and its loot reference model) and same-lineage merging for 12340.
- **Before S5/S7, measure the cMaNGOS dumps** (`Full_DB/TBCDB_1.11.0_Vengeance_One_A_Cmangos_Story.sql.gz`, 18.2 MB; `Full_DB/WoTLKDB_1_9_14092.sql.gz`, 30.0 MB) with the same counter, and fill in the "not measured" cells above.

### 6.2 Characters across versions (decision 6)

Under decision 1 a realm serves exactly one build, so this question only arises when a character moves between realms of different builds. One live character shared across versions would need merge rules for every progression system: experience, quests, loot, reputation, cooldowns, mail and auctions. Each of those rules is a place to lose data. So characters never cross builds live. They move by **transfer** (upward) or by **copy** (downward), and only when the operator enables it.

`Characters:CrossVersion`, set on the realm the character moves to:

| Value | Meaning |
|---|---|
| `Off` (default) | A character belongs to its build's realm. Nothing crosses. |
| `UpwardOnly` | A character may transfer to a realm of a higher build (5875 to 8606 to 12340). |
| `UpwardAndLegacyCopy` | Upward transfers as above, plus downward **legacy copies**. |

**Upward transfer** (e.g. 1.12 to 3.3.5) moves the character. Each later expansion is mostly a superset of the earlier one, so little is lost:
- Kept: level, experience, money, reputation, known spells, items, bank and mail. Items and spells map by id through build-ranged template data (decision 5's `min_build` keys). A per-pair mapping table names the ids whose meaning changed (see the spell id collision risk above). An id with no mapping fails closed: the transfer is refused, with a report, rather than guessing.
- Reset: talents, because the trees changed between versions. The points are refunded for the new tree.
- Dropped: quests that do not exist in the target build. A dropped quest-only item is moved to the version vault (below).

**Legacy copy** (e.g. a level-80 character to a 1.12 realm) never moves or changes the source character, which stays authoritative on its home realm. The target realm gets a new, independent character. After the copy the two progress separately, with no sync, so they cannot conflict.

| Part | Rule on the copy |
|---|---|
| Race/class | A combination the target build does not have (Blood Elf, Draenei, Death Knight in 1.12) is refused, with the reason. |
| Level | Clamped to the target's level cap (60 or 70). Experience restarts at the clamped level. |
| Spells | Rebuilt the way a fresh character of that class and level would have them: from the target build's trainer data, plus the class defaults. Spells from the source are not carried over one by one, because ranks and ids differ between builds. |
| Talents | Reset; the points are refunded for the target tree. |
| Equipped and carried items | Items that do not exist in the target build, or whose id means something else there, go to the **version vault**. Items that exist but need a higher level than the clamped one move from the equipment slots to the bags. When `Characters:CrossVersion:FillEmptySlots` is on (off by default), each empty equipment slot is filled with a level-appropriate item for the class, chosen by `.character boost`'s gear selection. |
| Money | Copied, then capped at the target's money cap. |
| Reputation, skills | Copied for factions and skill lines that exist in the target. Skill values are capped at the target's level maximum. |
| Currencies, achievements, glyphs, other expansion-only systems | Not copied. The target build has no place for them. |
| Quests | Not copied. The copy starts with an empty quest log. |

The **version vault** is a per-character store of items the current build cannot represent. The server keeps them and never sends them to the client. They come back when the character, or a later copy of it, lands on a build that can represent them. Nothing is ever deleted in a transfer or a copy.

Not planned: moving a character down for real (as opposed to copying it), and syncing progress between a source and its copies. Both would bring back the shared-character merge problem above.

When: this needs a target build's character data and templates, so it comes after S5 (TBC) and S7 (WotLK). Before then, `Characters:CrossVersion` stays `Off`, and the transfer code is not written.
